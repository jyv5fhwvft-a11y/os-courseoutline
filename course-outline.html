7 PHASES // 25 LECTURES
PHASE 1 • WEEKS 1–2

🏛️ Module 1: OS Structure & Design Model (Weeks 1–2)

Before we can look at individual managers, we must understand what the corporate building looks like.

The Asset Being Managed:
The boundary between the raw silicon hardware and the software applications.
The Core Problem:
How do we give programs access to powerful hardware without letting them accidentally destroy the system?
Prerequisite For:
Everything. It establishes the concept of "Kernel Mode" vs "User Mode" and the "System Call" pathway that all future managers rely on.
The Conceptual Flow:
L01: Lecture 1: The Architecture Matrix (Monolithic vs. Microkernels).
L02: Lecture 2: The Dual-Mode Barrier (User Space vs. Kernel Space).
L03: Lecture 3: The Gatekeeper Mechanism (System Calls and Hardware Traps).
PHASE 2 • WEEKS 3–5

🎭 Module 2: Process Management Model (Weeks 3–5)

Now that our architecture exists, we need to create the actors that will use it.

The Asset Being Managed:
The Central Processing Unit (CPU) time.
The Core Problem:
We have dozens of programs that want to run, but only a limited number of CPU cores. How do we share the processor fairly and fast?
Prerequisite For:
Process Synchronization and Memory Management. You cannot pass messages or allocate RAM until you have active, distinct execution contexts.
The Conceptual Flow:
L04: Lecture 4: Process Anatomy (The Process Control Block ledger).
L05: Lecture 5: The Thread Model (Lightweight concurrent workers sharing space).
L06: Lecture 6: Context Switching Mechanics (Saving and restoring CPU registers).
L07: Lecture 7: Scheduling Policies (First-Come-First-Served, Round Robin, and MLFQ).
PHASE 3 • WEEKS 6–7

🚦 Module 3: Process Synchronization Model (Weeks 6–7)

Now that we have multiple processes/threads running at the same time, they are going to bump into each other.

The Asset Being Managed:
Shared variables, global states, and cooperative workflows.
The Core Problem:
If two threads modify the exact same piece of data at the exact same microsecond, data gets corrupted (Race Conditions).
Prerequisite For:
File Systems and I/O Drivers (which heavily rely on locks to coordinate reading and writing data safely).
The Conceptual Flow:
L08: Lecture 8: The Critical Section Crisis (Identifying race conditions).
L09: Lecture 9: The Mutex Model (The exclusive bathroom key analogy).
L10: Lecture 10: The Semaphore & Condition Variable Model (Counting and signaling managers).
L11: Lecture 11: The Deadlock Gridlock (Coffman conditions and dependency chains).
PHASE 4 • WEEKS 8–10

🗺️ Module 4: Memory Management Model (Weeks 8–10)

Our processes are scheduled and can talk safely without crashing. Now, they need room to live and think.

The Asset Being Managed:
Physical Random Access Memory (RAM).
The Core Problem:
Programs are written assuming they own the entire computer's memory. How do we trick them into sharing one physical RAM chip without reading each other's secret data?
Prerequisite For:
File Systems (which use Virtual Memory tricks like Memory Mapping) and Security.
The Conceptual Flow:
L12: Lecture 12: Relocation Models (Base-and-bound sandbox boundaries).
L13: Lecture 13: The Paging Model (The translation matrix mapping virtual pages to physical frames).
L14: Lecture 14: The Fleeting Cache (Hardware sticky notes for address lookups).
L15: Lecture 15: Virtual Memory & Demand Paging (The library desk analogy—swapping blocks to the hard disk when RAM fills up).
PHASE 5 • WEEKS 11–12

🗄️ Module 5: File & Storage Management Model (Weeks 11–12)

Processes can run and use RAM, but the moment the power turns off, RAM wipes blank. We need a way to remember things permanently.

The Asset Being Managed:
Hard Drives, SSDs, and persistent non-volatile blocks.
The Core Problem:
The hardware disk only understands "Sector #4592". Humans understand "MyResume.pdf". How do we translate names into hardware locations?
Prerequisite For:
I/O Device Management (since storage is a specific class of block devices) and Security access control.
The Conceptual Flow:
L16: Lecture 16: Disk Geometry (Spinning magnetic plates vs. Solid-State silicon grids).
L17: Lecture 17: The File Abstraction & Directory Topology (The nested treasure boxes).
L18: Lecture 18: The Inode Architecture (The master metadata and block pointer ledger).
L19: Lecture 19: The Crash Consistency Model (Journaling and Write-Ahead Logging checkpoints).
PHASE 6 • WEEK 13

🔌 Module 6: I/O Device Management Model (Week 13)

Now that we can talk to storage disks, we can expand our reach to all other external hardware hardware (Keyboards, Displays, Network Cards).

The Asset Being Managed:
The Device Driver Ecosystem and I/O Controllers.
The Core Problem:
Every manufacturer makes hardware differently. The OS cannot contain code for 10,000 different keyboards. How do we create a single, unified interface for all hardware devices?
Prerequisite For:
Security and Protection (locking down hardware access).
The Conceptual Flow:
L20: Lecture 20: The I/O Communication Matrix (Polling, Interrupts, and Direct Memory Access / DMA).
L21: Lecture 21: Uniform Device Drivers (Block vs. Character vs. Network device models).
PHASE 7 • WEEKS 14–15

🔒 Module 7: Security & Protection Model (Weeks 14–15)

We have built a fully functional city with roads, offices, and warehouses. Our final job is to build the city walls and police force.

The Asset Being Managed:
System access permissions, isolation domains, and authentication parameters.
The Core Problem:
How do we ensure that user Alice cannot read user Bob's files, and that malware cannot exploit a bug to seize control of the entire Kernel?
The Conceptual Flow:
L22: Lecture 22: Protection Domains & Access Control Matrices (The master spreadsheet of who owns what).
L23: Lecture 23: Authentication & Program Exploits (Buffer overflows and privilege escalation).
L24: Lecture 24: Modern Isolation Paradigms (Sandboxing, Namespaces, and Containers).
L25: Lecture 25: Grand Course Retrospective (How all 7 managers operate simultaneously like a clockwork engine).
