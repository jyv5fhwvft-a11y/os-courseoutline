Module 1 — Foundations & Structure

L0 – L4

L0 — Course Introduction: What Problem Does an OS Actually Solve?

FOUNDATION

Objective: state in one sentence why an OS exists, and name the resources it arbitrates.

Hook: one computer, fifty people who each believe they own it entirely.

Breakdown: an OS is a referee, not a magic box. It exists because hardware is scarce and programs are selfish by default. History arc (compressed): batch processing → multiprogramming → time-sharing → modern personal/mobile/cloud systems, each step fixing a wasted-resource problem from the one before.

Terms to land: kernel, resource manager, abstraction.

Example: booting Linux today vs. a 1960s batch mainframe job queue.

Activity: open top/htop live and ask how many processes currently believe they own the CPU.

L1 — OS Components

ARCHITECTURE

Objective: distinguish kernel-space responsibilities from user-space tools.

Hook: the kitchen door rule — staff only.

Breakdown: the shell is the waiter taking your order; the kernel is the kitchen actually touching the stove.

Terms: kernel mode, user mode, shell.

Example: typing a bash command vs. the kernel handling a keypress interrupt.

Activity: run strace ls and sort the output lines into "shell did this" vs. "kernel did this."

L2 — System Call Interface

INTERFACES

Objective: explain how a user program requests a kernel service.

Hook: passport control — you hand documents to an officer who crosses the boundary for you.

Breakdown: read() is you asking the officer (kernel) to fetch something you're not allowed to touch directly (the disk).

Terms: syscall, trap, user/kernel boundary.

Example: read(), write(), fork() as concrete syscalls.

Activity: trace one syscall's full round trip on the board, step by step.

L3 — Kernel Design Philosophies

DESIGN

Objective: compare monolithic and microkernel trade-offs.

Hook: a giant Swiss Army knife vs. a tiny core that phones specialist tools for help.

Breakdown: monolithic is fast but one crash can take the whole kernel down; microkernel isolates failures but pays a messaging tax on every request.

Terms: monolithic kernel, microkernel, IPC.

Example: Linux (monolithic) vs. QNX/Minix (microkernel).

Activity: split the class in half, assign each side a design, and have them argue trade-offs using real failure scenarios.

L4 — The Boot Process

HARDWARE

Objective: sequence the stages between power-on and login prompt.

Hook: a relay race — each runner hands off the baton and drops out.

Breakdown: BIOS/UEFI checks hardware → bootloader locates and loads the kernel → kernel initializes → user-space services start.

Terms: UEFI, bootloader, init/systemd.

Example: GRUB loading a Linux kernel.

Activity: have students time their own laptop's boot and map the visible stages to the four steps.

02

Module 2 — Process Management

L5 – L9

L5 — What Is a Process?

CORE MODEL

Objective: define process state and describe what a PCB stores.

Hook: a process is a program mid-sentence — five actors can read the same script at once, each remembering a different line.

Breakdown: the PCB is the actor's bookmark — where they are, what they're holding, what comes next.

Terms: PCB, process states (new/ready/running/waiting/terminated), program vs. process.

Example: five terminal windows running the same shell binary.

Activity: narrate a scenario live and have students draw the resulting state diagram.

L6 — Process Creation & Context Switching

DISPATCH

Objective: trace what fork()/exec() do and explain why a context switch has a real cost.

Hook: swapping runners mid-relay without dropping the baton.

Breakdown: fork clones the runner; exec keeps the runner but hands them a new task; a context switch means carefully writing down exactly where the last runner stood before letting the next one onto the track.

Terms: fork, exec, context switch, PCB save/restore.

Example: how a shell launches every command you type.

Activity: live fork() demo in C — have students predict the output before running it.

L7 — CPU Scheduling I

SCHEDULING

Objective: apply FCFS, SJF, and Round Robin, and compute average wait time for each.

Hook: a grocery checkout line — serve people in arrival order, shortest-basket-first, or short timed turns for everyone?

Breakdown: FCFS is simple but lets one slow customer block the whole line; SJF minimizes average wait but requires predicting the future; Round Robin is fair but burns time on switching.

Terms: FCFS, SJF, Round Robin, quantum, average wait time.

Example: compute wait times for a four-job set under all three algorithms.

Activity: physically run the checkout-line scenario as a class exercise, then map the result to the math.

L8 — CPU Scheduling II

REAL-TIME

Objective: explain priority inversion and describe multilevel queue and real-time scheduling.

Hook: an ER waiting room — "first come first served" collapses the moment someone arrives bleeding.

Breakdown: pure priority scheduling can starve low-priority jobs forever; multilevel queues group jobs by type; real-time systems must guarantee a deadline, not just fairness.

Terms: priority inversion, starvation, aging, multilevel queue, real-time scheduling.

Example: a video call competing for CPU with a background virus scan.

Activity: construct a starvation scenario and have students propose the aging fix before you name it.

L9 — Threads & Concurrency Models

THREADS

Objective: distinguish user-level from kernel-level threads and state why threads exist.

Hook: one actor playing multiple roles on the same stage with the same props, unlike separate processes who each get their own stage.

Breakdown: a thread is a process's lightweight sibling — same address space, separate execution point.

Terms: thread, user-level thread, kernel-level thread, many-to-one / one-to-one / many-to-many models.

Example: a browser's tabs vs. its internal rendering threads.

Activity: open a task manager and have students guess which entries are processes and which are likely threads.

03

Module 3 — Process Synchronization

L10 – L11

L10 — Race Conditions & Mutual Exclusion

CONCURRENCY

Objective: identify a race condition and fix it with a lock.

Hook: a shared piggy bank — two kids "add a dollar" at the same instant and the bank ends up short.

Breakdown: the danger isn't the addition, it's the gap between reading the balance and writing the new one — anyone can barge in during that gap.

Terms: race condition, critical section, mutex, atomic operation.

Example: two threads incrementing a shared counter with no lock, producing a visibly wrong total.

Activity: run the broken counter live, get the wrong number as a class, add one lock() call, get the right one.

L11 — Classic Problems & Deadlock

DEADLOCK

Objective: describe Producer-Consumer and Dining Philosophers, and list the four deadlock conditions.

Hook: five philosophers, five forks, everyone grabs their left fork at once — nobody eats, nobody yields.

Breakdown: deadlock isn't a bug in any single philosopher's behavior, it's a trap built from four conditions all holding true at once.

Terms: mutual exclusion, hold-and-wait, no preemption, circular wait, semaphore.

Example: two database transactions each locking a row the other one needs.

Activity: have students break the deadlock by removing exactly one of the four conditions and argue which removal is cheapest in practice.

04

Module 4 — Memory Management

L12 – L15

L12 — Relocation Models

HARDWARE ADDR

Objective: explain base-and-bound protection and why programs can't assume fixed addresses.

Hook: hotel rooms — every guest thinks they're in "room 100," but the hotel silently maps that to whichever real room they're actually in.

Breakdown: the base register marks where your block starts, the bound register marks how big it is, and stepping outside either gets you stopped by hardware, not software.

Terms: base register, bound register, logical vs. physical address, relocation.

Example: two programs both compiled assuming they start at address 0.

Activity: manually compute physical addresses from logical ones given sample base/bound values.

L13 — The Paging Model

PAGING

Objective: translate a virtual address to a physical one using a page table.

Hook: a grid notebook mapping — each virtual "page number" is a numbered stub in a phonebook, translated on lookup.

Breakdown: memory gets sliced into equal-size pages and frames instead of one contiguous block, which eliminates external fragmentation.

Terms: page, frame, page table, page table entry, internal fragmentation.

Example: a 4KB page walking through a multi-level page table.

Activity: hand-walk a sample virtual address through a page table diagram to find its physical frame.

L14 — TLB Acceleration

HARDWARE MMU

Objective: explain why a TLB exists and calculate effective access time given a hit rate.

Hook: hardware sticky notes — instead of re-checking the same phonebook entry every time, you jot the answer somewhere faster to grab next.

Breakdown: without a TLB, every access costs two trips (page table, then memory); the TLB caches recent translations so most accesses cost one trip.

Terms: TLB, TLB hit/miss, effective access time.

Example: compute effective access time given a 90% hit rate, 1ns TLB, 100ns memory.

Activity: solve two effective-access-time problems, one with a poor hit rate, to show the cost of thrashing the cache.

L15 — Virtual Memory & Demand Paging

VIRTUAL MEMORY

Objective: describe demand paging and identify what a page fault actually is.

Hook: a library desk — you keep only a few books on your desk and send a runner to the stacks (disk) only when you reach for one that isn't there.

Breakdown: a page fault isn't necessarily an error, it's usually just "that page hasn't been fetched yet," and the OS handles it transparently.

Terms: demand paging, page fault, swap space, page replacement, thrashing.

Example: opening a 4GB video file on a machine with 2GB of RAM.

Activity: trace a page-reference string with FIFO and LRU by hand and compare fault counts.

05

Module 5 — File & Storage Management

L16 – L19

L16 — Disk Geometry

STORAGE HW

Objective: contrast mechanical HDD access with SSD access.

Hook: a record player needle sweeping to a groove vs. flipping a light switch — one pays travel time, one basically doesn't.

Breakdown: HDDs pay a real physical cost (seek time, rotational latency) that SSDs mostly skip, which is exactly why classic file system design obsessed over sequential layout.

Terms: platter, sector, seek time, rotational latency, SSD wear leveling.

Example: why defragmenting mattered for HDDs and is largely pointless for SSDs.

Activity: calculate total access time for a sequential vs. random read pattern on a spinning disk.

L17 — File Abstraction & Directory Topology

DIRECTORIES

Objective: explain how a hierarchical directory maps human-readable names to storage locations.

Hook: nested treasure boxes — a box inside a box inside a box, and the "path" is just the sequence of boxes you opened.

Breakdown: a directory is just a special file storing name-to-location mappings, not a fundamentally different kind of object.

Terms: file descriptor, path, hierarchical directory, hard link vs. soft link.

Example: /home/user/Documents/resume.pdf walked one folder at a time.

Activity: have students draw their own laptop's home-folder tree from memory, then check it.

L18 — Inode Architecture

INODES

Objective: describe what metadata an inode stores and how it locates a file's data blocks.

Hook: a ledger entry, not the treasure itself — the inode is the receipt telling you where the gold is buried and who owns it.

Breakdown: the filename lives in the directory entry; the inode it points to holds permissions, size, timestamps, and pointers to the real data blocks.

Terms: inode, inode number, direct/indirect block pointers, metadata.

Example: ls -i revealing a file's inode number.

Activity: given a small inode table and block map, have students manually reconstruct a file's contents location.

L19 — Crash Consistency

JOURNALING

Objective: explain how mid-write power loss corrupts a file system and how journaling prevents it.

Hook: writing a check in pencil before committing it in pen — jot the transaction in a scratch log first, so a mid-write power loss leaves a clear record of what actually finished.

Breakdown: journaling writes intent before committing the real change, so recovery just replays or discards the journal instead of guessing at a half-written disk.

Terms: journaling, write-ahead logging, fsck, atomic commit.

Example: ext4's journal vs. an unjournaled FAT32 volume after a forced shutdown.

Activity: walk through a "power loss at each possible moment" scenario and have students mark which moments are safe and which corrupt data without journaling.

06

Module 6 — I/O Device Management

L20 – L21

L20 — The I/O Communication Matrix

INTERRUPTS & DMA

Objective: compare polling, interrupts, and DMA as CPU-device communication strategies.

Hook: checking your mailbox every five minutes (polling) vs. the carrier ringing your doorbell (interrupt) vs. handing the carrier a key to put mail directly on your desk (DMA).

Breakdown: polling wastes cycles asking "done yet?"; interrupts free the CPU until tapped on the shoulder; DMA removes the CPU from the data transfer entirely.

Terms: polling, interrupt, interrupt handler, DMA controller.

Example: a network card using DMA to write packets straight into RAM.

Activity: rank a mouse, a hard-disk transfer, and a temperature sensor by which strategy fits best, and defend the choice.

L21 — Uniform Device Drivers

DRIVERS

Objective: classify a device as block, character, or network, and explain why a common interface matters.

Hook: a universal power adapter — the wall socket doesn't care whether you plug in a lamp or a laptop.

Breakdown: without a driver abstraction the kernel would need bespoke code for every manufacturer's every model forever; the driver model pushes that complexity behind a stable interface.

Terms: block device, character device, network device, driver, device file (/dev).

Example: /dev/sda (block) vs. /dev/tty (character) on Linux.

Activity: sort ten real devices — webcam, SSD, keyboard, Ethernet card, printer, and others — into the three driver categories.

07

Module 7 — Security & Protection

L22 – L28

L22 — Access Control

PERMISSIONS

Objective: apply an access control matrix and distinguish an ACL from a capability.

Hook: a hotel keycard system — one design asks "who's allowed into this room" (ACL, resource-centric), another hands you a physical key that simply works wherever it fits (capability, user-centric).

Breakdown: same goal, opposite bookkeeping — an ACL is a list attached to the resource, a capability is a token carried by the user.

Terms: access control matrix, ACL, capability, protection domain.

Example: a Linux file's rwx permission bits as a simplified ACL.

Activity: given a small access control matrix, answer a set of "can user X do Y" questions directly from the grid.

L23 — Authentication

AUTH FACTORS

Objective: compare password-based and biometric authentication and name a weakness in each.

Hook: proving who you are, three ways — something you know, something you are, something you have.

Breakdown: passwords can be stolen or guessed; biometrics can't be "reset" if compromised, which changes the entire risk calculation.

Terms: authentication factor, multi-factor authentication, salted hash.

Example: Windows Hello fingerprint unlock vs. a plaintext password field.

Activity: have students design a login flow for a banking app and justify which factors they'd require.

L24 — Program Exploits

EXPLOITS

Objective: explain how a buffer overflow hijacks control flow and name one mitigation.

Hook: overfilling a shelf until the extra boxes spill onto the neighbor's shelf and knock something important over.

Breakdown: writing past a fixed-size buffer's end can overwrite adjacent memory, including a function's return address, redirecting execution to code the attacker chose.

Terms: buffer overflow, stack smashing, return address, ASLR, stack canary.

Example: a classic strcpy()-into-fixed-buffer vulnerability.

Activity: diagram a stack before and after an overflow and identify exactly which byte overwrites the return address.

L25 — Encryption Fundamentals

CRYPTOGRAPHY

Objective: distinguish symmetric from asymmetric encryption and name where each shows up in practice.

Hook: a shared house key (symmetric, one key locks and unlocks) vs. a mailbox slot (asymmetric, anyone can drop mail in, only the key-holder takes it out).

Breakdown: symmetric is fast but requires securely sharing a secret key in advance; asymmetric solves that sharing problem but is too slow for bulk data, so real systems combine both.

Terms: symmetric encryption (AES), asymmetric encryption (RSA), key exchange, hybrid encryption.

Example: HTTPS/TLS using RSA to exchange a key, then AES to encrypt the actual traffic.

Activity: diagram the TLS handshake's key exchange step and label which algorithm handles which job.

L26 — Firewalls & Intrusion Detection

NETWORK SEC

Objective: distinguish a firewall's blocking role from an IDS's detection role.

Hook: a bouncer checking IDs at the door (firewall, blocks entry) vs. a guard watching camera feeds for suspicious behavior once people are already inside (IDS, detects and alerts).

Breakdown: a firewall enforces rules before traffic gets in; an IDS watches traffic already flowing and flags anomalies, without stopping anything itself.

Terms: firewall, port filtering, IDS, signature-based vs. anomaly-based detection.

Example: Windows Defender Firewall blocking an inbound port vs. an IDS flagging unusual outbound traffic at 3 a.m.

Activity: given a short traffic log, decide which entries a firewall rule would catch and which need an IDS instead.

L27 — Modern Isolation Paradigms

CONTAINERS

Objective: compare sandboxing, namespaces, and containers as isolation mechanisms.

Hook: a padded room (sandbox) vs. separate apartments in one building (namespaces) vs. a fully furnished apartment you can pick up and move to another building (containers).

Breakdown: a container isn't a new form of virtualization, it's namespaces and control groups wrapped in convenient tooling — the "lightweight VM" framing undersells what's actually a clever reuse of kernel features.

Terms: sandbox, namespace, cgroup, container, hypervisor (for contrast only).

Example: Docker container isolation vs. a full virtual machine.

Activity: list what a container shares with the host (the kernel) versus what it doesn't, and predict one attack a VM would block that a container wouldn't.

L28 — Grand Course Retrospective

SYNTHESIS

Objective: trace a single user action through all seven managers in sequence.

Hook: return to Lecture 0's fifty people who each believe they own the computer, and show exactly how all seven referees coordinate to keep that lie convincing.

Breakdown: walk "double-click a file icon" end to end — process creation, memory allocation, page faults, file system lookup, disk I/O, permission checks — as one continuous story instead of seven separate ones.

Terms: none new. This lecture is entirely synthesis.

Example: live-trace a single cat somefile.txt with strace, pointing out syscalls that touch nearly every module taught this semester.

Activity: give students a scenario ("a user opens a password-protected spreadsheet from a USB drive") and have them narrate what the OS does, module by module. Doubles as the final exam review session.

Assessment Architecture

GRADING FRAMEWORK
quiz

Weekly Quizzes

Weekly low-stakes quiz (5 questions, 10 minutes), given at the start of the session following each new topic. This catches misconceptions in Modules 2–4 before they compound, since each week's material assumes the last week's model held.

FREQUENCY: WEEKLY 10 MIN / TOPIC
terminal

Lab Track

Lab track, one per module:

  • Module 1: trace a syscall with strace.
  • Module 2: implement and benchmark two scheduling algorithms.
  • Module 3: fix a deliberately broken producer-consumer program.
  • Module 4: build a toy page-table simulator.
  • Module 5: implement a minimal inode-based file system on a RAM disk.
  • Module 6: write a character device driver stub.
  • Module 7: exploit a deliberately vulnerable buffer-overflow binary in a sandboxed VM, then patch it.
TOTAL LABS: 7 PRACTICAL C / LINUX
workspace_premium

Capstone Project

Capstone, assigned at the start of Week 9 (start of Module 5), due in the final week. Students choose one:

  1. Extend the Module 4 page-table simulator into a working demand-paging system with a page-replacement policy of their choice.
  2. Extend the Module 5 file system lab with crash consistency (journaling).
  3. Build a stripped-down chroot + namespace sandboxing demo as the Module 7 capstone.
DUE: FINAL WEEK CHOOSE 1 OF 3
