L14 Lecture 14: Race Conditions & Mutual Exclusion

🎯 Objective

Identify a data race condition inside a multi-threaded code block and refactor the code to guarantee mutual exclusion using a POSIX mutex lock.

🛑 Prerequisites

Module 3 (All Lectures), L09 (Threads & Concurrency).

🎪 Analogy 1 (Everyday Life)

The Shared Digital Piggy Bank. Imagine a digital piggy bank shared between two siblings (Threads) who can both add money at the same time. The bank currently holds $100. Siblings A and B both want to add 1 at the exact same instant. Sibling A reads the balance (100). Right before Sibling A can write down 101, Sibling B barges in, reads the balance (100), and writes down $101. Sibling A then finishes their turn and writes down $101. Even though two separate dollars were added, the bank ends up short because one update overwrote the other. This is a Race Condition. To fix it, we introduce a Mutex Lock—a single physical bathroom key taped to the bank. A sibling must grab the key, lock the room, change the balance in total isolation, and return the key.

💻 Analogy 2 (Pure Technical)

A Transactional Database Table Row Lock. A software mutex lock behaves identically to a hardware-enforced write-reservation token that blocks out raw processor access lines to a specific memory array address index until a commit sequence resolves.

🔗 System Cohesion Matrix

  • Relies On: Module 3 (Memory Management) — Requires threads pointing to identical shared virtual memory page coordinates to manifest a race state.
  • Feeds Into: L15 (Classic Problems & Deadlocks) — Introducing multiple independent mutex locks to protect complex data structures creates the precise architectural prerequisites for deadlock loops.

🔍 Core Breakdown

When multiple concurrent execution contexts read and modify a shared variable simultaneously, the final outcome depends entirely on the unpredictable order in which the instruction lines interleave. This vulnerability is a Race Condition, and the specific block of code executing the modification is the Critical Section.

To prevent corruption, we must enforce Mutual Exclusion—guaranteeing that only one thread can sit inside the critical section at any given time. This requires an atomic hardware instruction (like Test-and-Set or Compare-and-Swap) to verify and flip a Mutex flag in a single clock cycle without interruption.

🏷️ Lexicon / Terms

  • Race ConditionA concurrency bug where the system output shifts nondeterministically based on the precise timing and execution order of overlapping threads.
  • Critical SectionA structural window of source code that reads or writes to a shared, mutable global or heap state resource.
  • Mutual Exclusion (Mutex)A synchronization primitive that locks out concurrent access, ensuring only one execution thread can claim a resource slot.
  • Atomic OperationA low-level processor instruction sequence that executes completely to completion as a single indivisible unit without any possibility of preemption.

🛠️ Practical Example

// Refactoring a broken race-condition counter with a mutual exclusion lock
#include <pthread.h>
#include <stdio.h>

int shared_balance = 100; // Shared resource in the data segment
pthread_mutex_t bank_lock = PTHREAD_MUTEX_INITIALIZER; // The Mutex Primitive

void* add_dollar_routine(void* arg) {
    for(int i = 0; i < 10000; i++) {
        pthread_mutex_lock(&bank_lock);   // Acquire exclusive access / entry path

        // --- START CRITICAL SECTION ---
        shared_balance++;                 // Shared state modification block
        // ---- END CRITICAL SECTION ----

        pthread_mutex_unlock(&bank_lock); // Release lock / exit path
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, add_dollar_routine, NULL);
    pthread_create(&t2, NULL, add_dollar_routine, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("Final absolute guaranteed balance: $%d\n", shared_balance); // Always 20100
    return 0;
}

L15 Lecture 15: Classic Synchronization Problems & Deadlock Topologies

🎯 Objective

Diagram resource dependency graphs to locate a circular wait condition and eliminate a deadlock trap by stripping out one of the four Coffman parameters.

🛑 Prerequisites

L14 (Race Conditions & Mutual Exclusion).

🎪 Analogy 1 (Everyday Life)

The Dining Philosophers Dilemma. Imagine five philosophers sitting around a circular dinner table with exactly five forks total placed between them. To eat a bowl of noodles, a philosopher must pick up both their left fork and their right fork. Suddenly, all five philosophers reach out and grab their left fork at the exact same millisecond (Hold and Wait). Now, everyone holds one single fork, and nobody can grab their second fork because they are polite and refuse to rip a fork away from their neighbor (No Preemption). Everyone sits frozen staring at their food forever. This freeze is a Deadlock. To break it, the manager breaks the loop condition (Circular Wait) by forcing just one philosopher to grab their right fork first instead, shattering the lock gridlock immediately.

💻 Analogy 2 (Pure Technical)

Two Bank Databases Stuck in Recursive Cross-Account Transfer Requests. A deadlock matches a distributed system deadlock where Database Process A locks Row 1 and waits for Row 2, while Database Process B simultaneously locks Row 2 and blocks waiting for Row 1 to clear.

🔗 System Cohesion Matrix

  • Feeds Into: Module 5 (File & Storage Management) — Concurrent read/write systems inside virtual file systems rely heavily on nested lock trees, which can crash the entire OS via kernel deadlocks if paths cross.
  • Feeds Into: Module 6 (I/O Device Management) — Interrupt handler routines must be written to avoid locking resources held by preempted threads, preventing deadlocks inside Ring 0.

🔍 Core Breakdown

Synchronization primitives introduce complex resource interdependencies. A Deadlock is a state where a set of processes are permanently blocked because each process holds a resource and waits for another resource held by a different process in the same set.

A deadlock cannot occur unless all Four Coffman Conditions hold true simultaneously: Mutual Exclusion (unshareable locks), Hold-and-Wait (retaining locks while queuing for others), No Preemption (locks cannot be forcefully stolen), and Circular Wait (a closed loop chain of dependency). To prevent deadlocks, system designers must break at least one of these conditions (e.g., enforcing a strict global lock acquisition ordering hierarchy to prevent circular wait).

🏷️ Lexicon / Terms

  • DeadlockA critical gridlock error state where multiple competing threads are paralyzed permanently while waiting for a closed loop of dependencies to clear.
  • SemaphoreAn advanced signaling synchronization variable that maintains an internal integer counter to manage thread traffic access caps.
  • Coffman ConditionsThe definitive mathematical requirements (Mutual Exclusion, Hold & Wait, No Preemption, Circular Wait) that must all hold true for a deadlock to manifest.
  • Circular WaitAn execution condition where a closed ring of processes exists such that each process waits for a resource held by the next process in the sequence loop.

🛠️ Practical Example

// Simulating a deterministic Deadlock gridlock condition
#include <pthread.h>
#include <unistd.h>

pthread_mutex_t lock_A = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t lock_B = PTHREAD_MUTEX_INITIALIZER;

void* thread_one_routine(void* arg) {
    pthread_mutex_lock(&lock_A);    // Claims Lock A
    sleep(1);                       // Forces a preemption window context switch
    pthread_mutex_lock(&lock_B);    // Blocks waiting for Lock B held by Thread Two

    pthread_mutex_unlock(&lock_B);
    pthread_mutex_unlock(&lock_A);
    return NULL;
}

void* thread_two_routine(void* arg) {
    pthread_mutex_lock(&lock_B);    // Claims Lock B
    sleep(1);                       // Forces switch
    pthread_mutex_lock(&lock_A);    // Blocks waiting for Lock A held by Thread One

    pthread_mutex_unlock(&lock_A);
    pthread_mutex_unlock(&lock_B);
    return NULL;
}
// RESULT: Both threads hang indefinitely. The application freezes solid.
